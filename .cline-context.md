# Contexto del Proyecto - TipsterByte FX

## 🎯 Visión General
TipsterByte FX es un sistema de automatización para extracción de datos deportivos, 
incluyendo cuotas de apuestas, tablas de posiciones y calendarios de torneos.

## 🏗️ Arquitectura

### Patrón: DDD + Clean Architecture
```
backend/
├── apps/                    # Capa de Aplicación (por dominio)
│   ├── leagues_manager/     # Gestión de ligas deportivas
│   │   ├── api/            # Controllers y rutas
│   │   ├── application/    # Casos de uso (JobRunner)
│   │   ├── domain/         # Entidades, servicios, repositorios
│   │   ├── infrastructure/ # Implementaciones concretas
│   │   ├── scheduler/      # Jobs programados
│   │   ├── tasks/          # Tareas asíncronas
│   │   └── tests/          # Tests del módulo
│   └── platform_config/    # Configuración de plataforma
│       ├── api/
│       ├── domain/
│       ├── infrastructure/
│       └── tests/
├── core/                    # Capa de Dominio (compartido)
│   ├── db/                 # Conexiones DB (SQL + NoSQL)
│   ├── exceptions/         # Excepciones personalizadas
│   ├── logging/            # Configuración de logging
│   ├── monitoring/         # Monitoreo de procesos
│   ├── scheduler/          # Sistema de programación
│   └── services/           # Servicios compartidos
├── shared/                  # Código compartido
│   ├── constants/          # Constantes globales
│   └── repositories/       # Repositorios base
├── scripts/                 # Scripts de utilidad
└── commands/                # Comandos CLI
```

### Capas (de fuera hacia dentro):
1. **Infrastructure** (`infrastructure/`): Implementaciones concretas (DB, APIs externas)
2. **Application** (`application/`): Orquestación de casos de uso
3. **Domain** (`domain/`): Lógica de negocio pura
4. **API** (`api/`): Controllers HTTP (FastAPI)

## 🗄️ Bases de Datos

### PostgreSQL (SQLAlchemy)
- **Uso**: Datos estructurados (procesos, ligas, fuentes)
- **ORM**: SQLAlchemy 2.0
- **Migrations**: Alembic
- **Modelos**: `backend/apps/*/infrastructure/models/sql/`

### MongoDB (MongoEngine)
- **Uso**: Datos no estructurados (logs, resultados scraping)
- **ORM**: MongoEngine
- **Colecciones**: Configuradas en `backend/core/db/no_sql/`

## 🔄 Flujo de Ejecución de Procesos

1. **Scheduler** (`core/scheduler/`) programa jobs
2. **JobRunner** (`apps/leagues_manager/application/`) orquestra ejecución
3. **Robots** (`apps/leagues_manager/domain/robots/`) ejecutan tareas específicas
4. **ProcessRunRepository** registra ejecución en DB
5. **ProcessRunLog** registra logs detallados por paso

## 🤖 Sistema de Robots

### BaseRobot (Clase base)
```python
class BaseRobot:
    def execute(self) -> RobotResult:
        # Template Method Pattern
        self.before_execute()
        result = self.do_execute()
        self.after_execute(result)
        return result
```

### Robots Disponibles:
- `RobotScrapingGeneral`: Scraping genérico
- `RobotScrapingWPlay`: Scraping específico WPlay
- `RobotProcesamientoDatos`: Procesamiento de datos

## 📊 Monitoreo

### ProcessMonitor (`core/monitoring/`)
- **Patrón**: Observer + Strategy
- **Métricas**: Fiabilidad, duración, tasa de éxito
- **Persistencia**: `process_runs` + `process_run_logs`

### Métricas calculadas:
- **Fiabilidad**: (ejecuciones exitosas / total) × 100
- **Duración promedio**: tiempo promedio de ejecución
- **Tasa de error**: % de ejecuciones fallidas

## 🚀 Flujos Comunes

### Agregar nuevo Robot:
1. Crear clase en `apps/leagues_manager/domain/robots/`
2. Heredar de `BaseRobot`
3. Implementar `do_execute()`
4. Registrar en `jobs_loader.py`
5. Crear tests en `tests/`

### Agregar nueva API:
1. Crear controller en `apps/*/api/v1/routes/`
2. Definir schemas Pydantic en `api/schemas/`
3. Registrar rutas en `main.py`
4. Crear tests en `tests/`

### Modificar modelo DB:
1. Modificar modelo en `infrastructure/models/sql/`
2. Crear migration: `alembic revision --autogenerate`
3. Revisar migration generada
4. Aplicar: `alembic upgrade head`
5. Actualizar tests
