# Instrucciones Específicas por Tipo de Tarea

## 🎯 Plantillas de Instrucciones

Cuando el usuario te pida algo, identifica el tipo de tarea y sigue las instrucciones correspondientes.

---

## 🔧 TIPO 1: Corrección de Bug / Error

### Identificación:
- Palabras clave: "error", "bug", "no funciona", "falla", "problema", "arregla"
- Ejemplo: "Hay un error en el script de diagnóstico"

### Instrucciones:
1. **Analizar** el error proporcionado por el usuario
2. **Leer** el archivo mencionado completamente
3. **Identificar** la causa raíz del problema
4. **Explicar** brevemente qué causaba el error
5. **Corregir** usando `replace_in_file` con bloques SEARCH/REPLACE
6. **Probar** ejecutando el comando apropiado
7. **Verificar** que el error se resolvió

### Ejemplo de flujo:
```
Usuario: "El script diagnose_processes_visual.py muestra [ERR] para todos los procesos"

Respuesta:
1. Leo el archivo
2. Identifico que usa ProcessMonitor() que está vacío
3. Explico: "El problema es que ProcessMonitor almacena métricas en memoria"
4. Corrijo: Agrego función get_reliability_from_db()
5. Pruebo: python backend/scripts/diagnose_processes_visual.py
6. Verifico: El script ahora muestra datos reales de la DB
```

## 🎨 Formato de Respuesta Estándar

Para CUALQUIER tipo de tarea, siempre incluir:

### 1. Resumen Ejecutivo (1-2 líneas)
```
"He corregido el script de diagnóstico para que lea datos de la DB en lugar de memoria."
```

### 2. Cambios Realizados (lista)
```
- Eliminado: ProcessMonitor (almacenaba datos en memoria)
- Agregada: Función get_reliability_from_db()
- Corregidos: Tipos de SQLAlchemy
- Probado: Script ejecutado exitosamente
```

### 3. Resultado / Verificación
```
✅ El script ahora muestra fiabilidad real desde process_runs
```

### 4. Siguientes Pasos (si aplica)
```
Para mejorar aún más:
- Agregar métricas de duración promedio
- Incluir gráficos de tendencia
```

## ⚠️ Errores Comunes a Evitar

1. **No** modificar archivos sin leerlos primero
2. **No** asumir que imports existen sin verificar
3. **No** crear archivos sin verificar que directorio existe
4. **No** usar `write_to_file` cuando `replace_in_file` es apropiado
5. **No** olvidar agregar imports necesarios
6. **No** romper tests existentes
7. **No** exponer credenciales en código

## 🔍 Búsqueda de Información

### Antes de implementar algo nuevo:
1. **Buscar** si ya existe implementación similar
2. **Revisar** `backend/shared/` para código reutilizable
3. **Verificar** `backend/core/` para funcionalidades base
4. **Consultar** tests existentes para patrones

### Comandos de búsqueda útiles:
```python
# En search_files tool:
regex: "class.*Robot"  # Buscar clases Robot
regex: "def.*reliability"  # Buscar funciones de fiabilidad
regex: "process_run"  # Buscar referencias a process_run
